# grid-coverage

**grid-coverage** finds a path that visits the most unique cells on a grid with some cells blocked. It starts from a chosen cell and takes at most MAX_STEPS steps. Backtracking over already-visited cells is allowed but costs a step.

`main` program reads a grid in one of two formats:
- ascii representation, where `#` - blocked cell, `.` - free cell.
- DIMACS-like format, file is a list of rows, cols and which cells are blocked.

The program automatically chooses a start cell by computing additional information about the grid (see: preprocessing.h). Each walk algorithm explores the grid in four directions: north, south, east or west. At the end, the program outputs a list of coordinates in the path and the number of distinct cells visited.

## Build

To build the project you need `gcc` and `make`.

```
make all
```

This command builds two groups of binaries:
- `build/main` - parses input graphs (either stdin or file) and runs chosen algorithm.
- `build/generators/random`, `build/generators/maze`, `build/generators/components` - grid file generators.

**Build options:**

| Target | Effect |
|---|---|
| `make` | Release build with `-O2` |
| `make debug` | Debug build with `-O0 -g3 -DDEBUG` (cleans first) |
| `make verbose` | Release build with `DEBUG` prints enabled |
| `make clean` | Remove `build/` and `tests/build/` |

In debug mode, the program prints a colored grid with arrow glyphs (`^>v<`) showing the walk path. The start cell is green and the end cell (`E`) is red. This output works only for grids with at most 200 rows and 400 columns.

## Run

```
./build/main ALGORITHM MAX_STEPS [FILE]
```

- `ALGORITHM`: one of `deep`, `random`, `warnsdorff`, `heuristic`
- `MAX_STEPS`: a positive integer (absolute steps) or a decimal (fraction of total cells, e.g. `0.25`)
- `FILE`: path to an ascii representation of grid. If you omit it, the program reads a cell-list grid from stdin.

**Examples:**

```
./build/main deep 50 data/example2.ascii
./build/main heuristic 0.25 data/benchmark/maze_101_101_0.1.ascii
./build/main warnsdorff 100 < data/example1.graph
```

The program always runs the algorithm from every good start (see: `grid_good_start` in `preprocessing.h`). If no good start is found, it tries every free cell.

Output format: `(0,0), (0,1), ..., 42` - coordinates followed by the unique-cell count.

Additionally, a script `run_benchmark.sh` is provided. It automatically runs all algorithms on data from `data/benchmarks`. You can pass `--no-paths` to this script to silence outputting result paths to the console and `results/paths` files.

## File formats

Two grid input formats are supported:

**ASCII grid**
```
###...
#.#...
....#.
...#..
```
`.` is a free cell. `#` is a blocked cell. Every row must have the same width (checked by `main.c` parser).

**Cell-list**
```
8 8
2 0
2 1
3 3
```
The first line gives rows and columns. Each later line gives the row and column of one blocked cell. All other cells are free. This format is only used when `main.c` reads from stdin.

## Generate

Three different types of grids are generated by the `generators/` scripts.

### Random

```
./build/generators/random ROWS COLS P OUTPUT_FILE [CELL_LIST]
```

Marks each cell as blocked with probability `P` (a decimal between 0 and 1).
Add `CELL_LIST` as the last argument to write a cell-list file instead of an ASCII grid.

**Example usage:**
```
./build/generators/random 50 50 0.3 data/random_50_50_0.3.ascii
```

### Maze

```
./build/generators/maze ROWS COLS P OUTPUT_FILE [CELL_LIST]
```

Builds a maze with randomized Prim algorithm. `P` sets the probability of removing a wall to create a loop. Set `P` to 0 for a perfect maze.
Add `CELL_LIST` as the last argument to write a cell-list file instead of an ASCII grid.

**Example usage:**
```
./build/generators/maze 51 51 0.1 data/maze_51_51_0.1.ascii
```

### Components

```
./build/generators/components ROWS COLS K MIN_SIZE MAX_SIZE OUTPUT_FILE [CELL_LIST]
```

Creates `K` open components that do not touch. Each component has a random size between `MIN_SIZE` and `MAX_SIZE`.
Add `CELL_LIST` as the last argument to write a cell-list file instead of an ASCII grid.

**Example usage:**
```
./build/generators/components 50 50 5 5 20 data/components_50_50.ascii
```

`generate_benchmark_data.sh` script creates all benchmark files at once at `data/benchmark`:

```
./generate_benchmark_data.sh
```

## Test

```
make test
```

This command builds each file in `tests/` as a standalone binary and runs it. At the end tests output summary with total number of tests and number of failed tests.

```
make debug_test
```

This command runs the same tests under `valgrind --leak-check=full` and with debug prints.

## Benchmarks

`generate_benchmark_data.sh` creates all benchmark grids in `data/benchmark`. Run benchmarks with `run_benchmark.sh`:

```
MAX_STEPS=0.25 ./run_benchmark.sh --no-paths
```

`MAX_STEPS` accepts an integer or a fraction of total cells. Results are written as CSV to the stdout (use `| tee filepath` to save to file). The CSV columns are: dataset, algorithm, max_steps, unique_cells, elapsed_sec, bytes_allocated, leaks (yes/no).

Pre-generated results exist in `results/` for MAX_STEPS values of 0.05, 0.15, 0.25, and 0.5 times cell count. See [results/RESULTS.md](results/RESULTS.md) for a table of unique-cell counts per dataset and algorithm.

Overall, all algorithms except `random` produce similar results. `random` often visits 2x fewer unique cells.

Optimal values for `data/benchmark` grids are not known. This problem is NP-complete (reduction from Hamiltonian path). Still, the algorithms often produce values close to the MAX_STEPS budget.

# Project in-depth

## Code structure

```
src/            Library and entry point
  main.c        CLI entry point, argument parsing, grid I/O
  lib/          Single-header library modules
    lib.h         Aggregate include (all modules, in order)
    cell.h        Flat-index cell type and direction helpers
    debug.h       Conditional print macros
    grid.h        Grid data structure
    parse.h       String-to-number parsing
    path.h        Walk path (ordered list of cells)
    preprocessing.h  Grid analysis pipeline
    queue.h       Ring-buffer FIFO queue
    stack.h       LIFO stack
    walk.h        Walk algorithms
generators/     Grid file generators
  components.c   Connected components separated by blocked cells
  maze.c         Maze grids (randomized Prim, optional wall removal)
  random.c       Random blocked-cell grids
tests/          Unit and smoke tests
```

### `cell.h`

A cell is a flat `size_t` index into a row-major grid. `cell_from_row_col` computes a flat index cell from cell's row and column values. `cell_row` and `cell_col` extract coordinates from flat index. `cell_neighbour` moves one step in a given direction. It rejects wrap-around at row and column boundaries.

### `grid.h`

The grid stores rows, columns, and a `bool` array (one element per cell). `true` means blocked. `grid_new_with_blocked` creates a grid from a list of blocked-cell coordinates. `grid_at` and `grid_at_flat` are used for cell-state lookup. The struct uses a FAM (flexible array member) for one-allocation construction.

### `parse.h`

`parse_size`, `parse_int`, `parse_double`, and `parse_pair` convert strings to numbers. Each function rejects empty input, negatives where not valid, trailing garbage, and overflow. They use standard-library `strtol`/`strtod` with end-pointer verification.

### `path.h`

A path is an ordered list of `cell` elements stored in a FAM buffer. `path_push` and `path_pop` are essentially stack operations. `path_unique_cells` counts distinct cells in O(n^2) time - it is called only once, at the end of a walk. `path_print_on_grid` renders the walk onto the grid with arrow glyphs (debug builds only).

### `queue.h` and `stack.h`

Both are fixed-capacity containers over FAM `size_t` arrays, built for iterative DFS and BFS in the preprocessing pipeline. `queue` is a ring buffer. `stack` is a push-pop LIFO. All operations are O(1). Both reject zero-capacity creation.

### `preprocessing.h`

The pipeline runs five steps in a fixed order. Each step depends on the previous step.

| Step | Function | Time | What it computes |
|---|---|---|---|
| 1. Cut vertices | `grid_cut_vertices` | O(V+E) | Marks cells whose removal disconnects the component |
| 2. Cut distances | `grid_cut_distances` | O(V+E) | Shortest-path distance from each cell to the nearest cut vertex |
| 3. Components | `grid_components` | O(V+E) | Assigns a component ID to each free cell |
| 4. Neighbours | `grid_calculate_neighbours` | O(V) | Precomputes the flat index of each neighbour (N/S/E/W) and neighbour count |
| 5. Good starts | `grid_good_start` | O(V) | Marks the best start cells (largest component, farthest from cuts, fewest neighbours) |

Steps 1–3 use iterative search with the custom `stack` and `queue` types. No recursion is used. Step 4 precomputes neighbour indices so walk algorithms do not recompute them at every step. Step 5 picks start cells that give the best chance for a high-coverage walk.

The context struct holds per-cell metadata:

- `component_id` (`uint32_t`) - component label
- `cut_distance` (`uint32_t`) - BFS distance to nearest cut vertex, `UINT32_MAX` if none
- `neighbour_count` (`uint8_t`) - number of free neighbours
- `neighbour_north/south/east/west` (`size_t`) - flat index of each free neighbour, `SIZE_MAX` if none
- `is_cut_vertex`, `is_good_start` (`bool`)

Total memory: ~48 bytes per cell. The context and its cell array live in one FAM allocation. Component sizes live in a separate allocation.

### `walk.h`

Four walk algorithms are implemented. All accept a start cell and return a `path*`. The caller frees the path.

| Algorithm | Time | Memory | Deterministic |
|---|---|---|---|---|
| Deep walk | O(max_steps) | O(N + max_steps) | Yes |
| Random walk | O(max_steps) | O(N + max_steps) | No (seeded) |
| Warnsdorff walk | O(max_steps) | O(N + max_steps) | Yes |
| Heuristic walk | O(max_steps) | O(N + max_steps) | Yes |

where N = rows * cols.

**Deep walk** does iterative DFS. From the current cell, it moves to the first unvisited free neighbour in N/S/E/W order. When no unvisited neighbour is left, it backtracks along the DFS frontier. It stops when the frontier is empty or `max_steps` is used up.

**Random walk** generates all random numbers upfront from a seed. At each step it prefers unvisited neighbours. If none are available, it picks a visited neighbour. This makes it reproducible for a given seed. The program passes `time(NULL)` as the seed.

**Warnsdorff walk** uses the Warnsdorff heuristic: at each step it picks the unvisited neighbour with the fewest unvisited neighbours of its own. Ties break by largest component size, then farthest cut distance (in that order). This drives the walk toward dead-ends first.

**Heuristic walk** uses a composite score:
```
score = unvisited_neighbours * 1000
      - component_size * 10
      - cut_distance * 1
      + (is_cut_vertex ? 10000 : 0)
```
Lower is better. The Warnsdorff term dominates (factor 1000). The cut-vertex penalty (10000) overrides everything - the walk avoids cut vertices when an alternative exists.

All algorithms that explore neighbours use the precomputed neighbour indices from step 4 of preprocessing.

## Potential improvements

### Memory packing

The `cell_info` struct uses ~48 bytes per cell. With packing:
- Store grid cells as `uint64_t[]` bitsets (1 bit per cell instead of 1 byte).
- Shrink `component_id`, `cut_distance`, and neighbour indices to `uint16_t` or `uint32_t` when the grid is small.
- Merge `is_cut_vertex`, `is_good_start` flags into a single `uint8_t` bitfield.
- Use `uint16_t` for `rows` and `cols` in `grid` and `grid_context` - the current walk algorithms are expensive on grids larger than 65,535 cells per dimension.

### Multithreading

Walk algorithms need no locks. Each inner-algorithm call reads the grid and context (both constant) and writes only its own `visited` array and `path`. You can run every good-start candidate in parallel and merge results at the end. Preprocessing needs more thought - the five pipeline steps have sequential data dependencies. However, component detection could process separate components in parallel after a shared labeling pass.

### Additional walk algorithms

- **Beam search** : keep K best partial paths at each step, extend each by all possible moves, keep the top K. This escapes local minima at the cost of O(K * N^2) time.
- **Tabu search**: after a deep walk, search the neighbourhood by forbidding recently visited edges and re-running. This can escape local optima.
- **BFS-layer greedy**: precompute BFS distances from the start cell. At each step, move to the unvisited neighbour with the smallest distance. This fills the grid in concentric layers and minimizes backtracking on tree-like maps.
- or any other metaheuristic or informed search approach may be feasible here

### Additional preprocessing

- Build a component graph over cut vertices. This lets the walker analyze component connectivity globally rather than locally.
- Compute articulation-point weight - how many cells become unreachable if a given cell is visited last among its neighbours. This gives a better cut-vertex penalty than the binary flag.
- Compute all-pairs distances within each component with a second BFS pass. This supports lookahead heuristics that consider reachable frontier size.

### `path_unique_cells`

`path_unique_cells` counts distinct cells in O(N^2) time. Each walk algorithm already maintains a `visited` array with O(1) lookups. Return the unique count from the algorithm directly instead of scanning the path afterwards.
